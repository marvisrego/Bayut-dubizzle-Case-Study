## Data and source of truth

- Original input: Cars_data.xlsx, using both raw dataset and cleaned dataset sheets (100 populated rows each). Do not modify the original workbook.
- Canonical input for ingestion: data/processed/cars_merged.xlsx, merged_inventory sheet. It is generated by scripts/prepare_inventory.py. The matching CSV is an export. merge_log, conflicts, duplicate_review, and data/processed/merge_audit.md preserve audit details.
- The merge produces 189 canonical listings from 200 source rows: 8 exact duplicate groups and 11 merged source rows. IDs are stable CAR_0001-style identifiers. The fingerprint uses normalized year, make, model, trim, title, and description. Different fingerprints within a year/make/model block remain separate. source_refs and original fields preserve source lineage.
- PostgreSQL cars is the factual source. It retains the 23 canonical workbook fields, nullable price_aed and mileage_km, and price_evidence and mileage_evidence excerpts. The workbook has no dedicated price, mileage, color, body type, managed-car, or availability column.
- app/services/vehicle_facts.py extracts explicit purchase prices and odometer readings from English and Arabic source text during ingestion. It excludes monthly installments, fees, speed and EV range figures, and warranty or service distance limits. Examples: CAR_0005 is AED 115,750 in cash and 18 km; CAR_0025 has an Arabic AED 105,000 price and 150,000 km odometer; CAR_0003 has no verified odometer despite a 100,000 km warranty limit. Unsupported facts stay null.
- The older preprocess_inventory.py and data/inventory_enriched.csv are exploratory cleaned-sheet-only artifacts. Their inferred body types are not authoritative listing facts.

## Architecture and interfaces

- scripts/ingest_inventory.py reads the canonical workbook, creates/migrates PostgreSQL tables, upserts all cars and extracted facts, indexes changed listing text, and verifies source/database/vector state. Unchanged source/model hashes skip NVIDIA listing embeddings. Qdrant holds listing IDs and small filter metadata, not the complete factual record.
- app/services/car_repository.py runs deterministic SQL filters. app/services/retrieval.py provides structured_search, semantic_search, and hybrid_search. Hard SQL constraints define eligible IDs before vector ranking; complete result records are fetched from PostgreSQL. A null price or mileage never passes a numeric hard filter.
- app/services/nvidia_chat.py calls the configured NVIDIA chat model with allowlisted tool schemas and the shared 40-request/minute limiter. app/services/agent.py orchestrates tools and builds grounded replies. app/services/agent_policy.py resolves first/second/third and pronoun references, validates planner-proposed filters against user wording, and applies scope and factual-answer rules. The LLM does not write SQL or invent listing details.
- app/services/memory.py stores users, sessions, chat messages, explicit session state (ordered last_search_ids, selected_listing_id, active_filters, created_at, updated_at), long-term preferences, and liked cars in PostgreSQL. The LLM receives a compact profile, session state, current message, and at most eight recent messages. A temporary search filter does not automatically become a lasting preference.
- app/services/leads.py upserts lead data to PostgreSQL and atomically exports local data/leads.csv. The CSV is gitignored. The conversation gathers stated make/model/body type, budget, needs, and contact details, with follow-up prompts for missing information.
- app/services/booking.py validates a future viewing/test-drive slot in Dubai time: Monday to Saturday, 08:00 through 20:00. It stores a simulated booking request with pending_confirmation status. All canonical listings are treated as dubizzle managed in this prototype. There is no dealer availability feed or confirmed reservation.
- FastAPI routes in app/api/routes.py: GET /health; POST /users; POST /sessions; GET /sessions/{session_id}; POST /chat; GET /cars/{listing_id}; POST /cars/search; POST /bookings. POST /users maps a normalized display name to a persistent UUID via user_names in PostgreSQL. POST /chat accepts session_id, message, and optional user_id, which must match the session owner. It returns message, session_id, cars, listing_ids, and optional next_input.
